# Rozszerz Artifact Server, nie buduj viewera od zera

**Werdykt: rozszerz.** Rdzeń tego, czego szukasz, już istnieje. Artifact Server deklaruje lokalną bibliotekę projektów, wątkowe komentarze przypięte do elementów, odczyt i odpowiedzi agenta przez MCP, niezmienne wersje i sandbox dla JS ([repo](https://github.com/plannotator/artifact-server)). Żadne narzędzie nie zamyka jednak całości: nie znalazłem niczego, co wiąże zarządzany dokument z branchem lub PR-em bez commitu, ani karteczki nieprzeznaczonej dla agenta. Nie buduj więc viewera. Zbuduj cienki plugin Claude Code ze skillem wspólnego stylu i hookami zapisującymi repo, branch i PR, bo ten plugin jest potrzebny przy każdym silniku i to on leczy niespójny wygląd oraz większość gubienia dokumentów. **Jedyny następny krok: pół dnia na uruchomienie Artifact Server na tym Windowsie z parą dokumentów Silos.** Jeśli test padnie, budujesz wąski własny viewer według architektury opisanej niżej. Zastrzeżenie jest poważne: żadnego kandydata nie zainstalowano ani nie uruchomiono, więc matryca pokazuje deklaracje z README i specyfikacji, a obsługa Windows pozostaje niezweryfikowana.

## Dziewięciu kandydatów, żaden nie leczy wszystkich bólów

Matryca ma kolumny ułożone według wagi, nie według listy funkcji. „Ból” to Twoje trzy skargi: gubienie, różny wygląd, brak komentowania i oznaczania. „Warunek” to ograniczenie, którego nie da się obejść. „Później” to funkcje mile widziane. T = tak, C = częściowo, N = nie, ? = dokumentacja nie rozstrzyga. Suma liczy T jako 1, C jako 0,5 i służy tylko do orientacji. Wszystkie komórki są deklaracjami, statystyki pochodzą z GitHub API z 5 listopada 2026.

Remis na górze jest pozorny. LiveFolio ma 2 gwiazdki, licencję AGPL-3.0, nie opisuje Windows ani wątków ([repo](https://github.com/LiveFolio-Cloud/LiveFolio-oss)), a Artifact Studio nie ma deklarowanej licencji i jest aplikacją na pasek menu Maca ([Getting Started](https://raw.githubusercontent.com/kaiketsu-labs/artifact-studio/main/docs/GETTING-STARTED.md)). Artifact Server ma licencję MIT lub Apache-2.0, 344 commity, ostatni push z 4 listopada i wątki przypięte do jednej konkretnej wersji ([spec komentarzy](https://github.com/plannotator/artifact-server/blob/main/project/spec/artifact-comments-spec.md)). Plannotator jest najdojrzalszy (9 863 gwiazdki, 5 430 commitów) i ma najlepiej udokumentowany Windows, ale daje przeglądarkę plików tylko na sesję, nie trwałą bibliotekę, i nie opisuje wątków ([docs](https://docs.plannotator.ai/learn/annotate-any-web-page-or-html-file)). To plan B dla pętli komentarzy, nie silnik biblioteki.

**Claude Artifacts odpadają na lokalności, nie na renderowaniu.** Dokumenty Silos zmieściłyby się w ich limitach: inline JS działa, Google Fonts są dozwolone, limit to 16 MiB. Nie ma jednak trybu lokalnego, a treść leży na infrastrukturze Anthropic ([docs](https://code.claude.com/docs/en/artifacts)). Nie znaleziono pól repo, brancha ani PR-a, a inna sesja tworzy nowy artefakt, jeśli nie dostanie adresu, więc ciągłość dokumentu zależy od tego, czy agent zna link. Komentarze opisano dla udostępniania w organizacji, a pętla dla solo Pro/Max nie jest wyjaśniona. Do tego otwarte zgłoszenie mówi o pustym tekście przy odczycie komentarzy ([#102872](https://github.com/anthropics/claude-code/issues/102872)). Zostają kanałem pokazania pojedynczego dokumentu komuś innemu, nie biblioteką.

**Realne luki dla Ciebie są dwie.** Pierwsza to powiązanie z repo, branchem i PR-em, bo przy gubieniu to właśnie kontekst pracy mówi, gdzie szukać. Najbliżej są Crit, który wiąże recenzje z branchem i synchronizuje PR ([README](https://github.com/tomasz-tomczyk/crit)), oraz web-artefacts, który zna tylko nazwę repo ([README](https://github.com/lbug/web-artefacts)). Druga to karteczka, którą spośród znalezionych narzędzi reklamuje tylko hostowany coeditHTML ([repo](https://github.com/Mason-Levyy/coedithtml-monorepo)). Luka ta jest mniejsza, niż wygląda. Napisałeś „nie zawsze dla agenta”, a to nie to samo co tajność, więc solo wystarczy filtr po stronie skilla zamiast widoczności na serwerze. Komentarz z typem karteczki w kotwicy, która jest nieprzezroczystym JSON-em klienta do 16 KiB ([spec](https://github.com/plannotator/artifact-server/blob/main/project/spec/artifact-comments-spec.md)), albo na start prefiks w treści, załatwia podział „dla agenta / dla mnie”. Wizualne odróżnienie karteczki wymaga już zmiany w UI: forka lub PR-a upstream. To moja propozycja, nie sprawdzona.

Pozorne luki też trzeba nazwać. Odczyt przez agenta, styl, sandbox i hosting są dobrze pokryte. Platformy nie ratują sytuacji: Obsidian daje powłokę, ale nie znaleziono wtyczki łączącej żywy JS z przypiętymi komentarzami, a najmocniejszy viewer ma 742 pobrania ([HTML Reader-plus](https://community.obsidian.md/plugins/html-reader-plus)). Komentarze w VS Code i Cursorze to wejście do promptu, nie trwały rejestr ([VS Code 1.132](https://code.visualstudio.com/updates/v1_132), [Cursor](https://cursor.com/docs/agent/design-mode)).

## Para Silos zmienia priorytety: wersja i rodowód przed diffem

Pomiar na Twoich plikach w `C:\Users\bakie\projects\silos` podważa założenie, że wizualny diff jest główną brakującą funkcją. `Silos-pivot-lamiglowki.html` (114 KB) i `-v2.html` (167 KB) dzielą 10 z 36 identyfikatorów i zachowują od 4 do 6 z około 19 sekcji. **Żaden z 329 bloków tekstu (co najmniej 30 znaków) nie jest identyczny nawet po normalizacji**, tylko 5% bloków v1 ma odpowiednik w v2 przy word-Jaccard co najmniej 0,3, a 1% przy 0,5. Dokładnie zgadza się 158 z 753 długich linii, prawdopodobnie CSS i JS.

To przepisanie całego dokumentu. Kotwiczenie po stabilnych ID i rozmytym tekście by tu zawiodło, a diff pikselowy lub strukturalny powiedziałby niewiele. To jedna para, więc nie uogólniam, ale wnioski są konkretne. Komentarz należy do konkretnej wersji, co Artifact Server już deklaruje. Przeniesienie otwartych wątków robi agent, nie algorytm, jak w tdoc, gdzie `/tdoc edit` czyta komentarze, tworzy wersję i odpowiada na każdy ([README](https://github.com/tornado-doc/tdoc)). Notatka agenta „co się zmieniło” jest ważniejsza niż wizualny diff, a na start wystarczy widok obok siebie. Render diff i linki między dokumentami zostają na później: nie leczą żadnego z trzech bólów, a Plannotator pokrywa diff tekstowy, gdyby okazał się potrzebny ([docs](https://docs.plannotator.ai/open-source/workflows/html)).

Wersjonujesz nazwą pliku (`-v2`), więc „ten sam dokument” musi być śledzonym rodowodem, nie ścieżką. Lavish kluczuje sesje kanoniczną ścieżką ([README](https://github.com/kunchenguid/lavish-axi)), więc `-v2` byłby u niego nowym dokumentem. Model publikacji w Artifact Server pozwala skillowi kazać agentowi publikować kolejną wersję tego samego artefaktu, a stabilny identyfikator w `<meta>` utrzyma rodowód między sesjami.

Plik v2 jest nieśledzony na branchu `m1-final`, a `Silos-GDD.html` z tego samego repo jest śledzony. To żywy przykład dokumentu obok kodu bez commitu, więc metadane muszą leżeć poza repo. Dokumenty te mają 20 sekcji, 10 elementów svg, 9 details, 1 skrypt inline i 13 wywołań `Math.random` w generatorze uruchamianym przyciskiem, bez `localStorage` i `fetch`, za to z Google Fonts z sieci. Sandbox z `allow-scripts` i zezwoleniem na fonty powinien tu wystarczyć. Spójność stylu jest bliżej, niż się wydaje: 16 z 28 zmiennych CSS jest wspólnych z GDD, ale rodziny fontów się różnią, co potwierdza „każdy wygląda inaczej”. Te 16 zmiennych to gotowy zaczątek skilla, a [effective-html](https://github.com/plannotator/effective-html) (MIT, 3 968 gwiazdek) daje bazę.

## Plugin obsługuje agenta, ale nie wyrenderuje dokumentu

Plugin Claude Code musi objąć stronę agenta, bo tam powstaje dokument. Skill daje styl, szablony i obowiązek rejestracji. `PostToolUse` na `Write|Edit` dostaje `session_id`, `cwd` i ścieżkę, ale nie repo, brancha ani PR-a, więc hook wyprowadza je z `git` i `gh` ([Hooks](https://code.claude.com/docs/en/hooks)). Pliki pisane przez Bash wymagają przeglądu w `Stop`, a PR często jeszcze nie istnieje, więc wiązanie musi być późne, po nazwie brancha przy oglądaniu. SessionStart może wstrzykiwać listę dokumentów brancha i wątków bez odpowiedzi. Bez forka grupowanie da się osiągnąć przez układ „projekt = repo”, a branch, SHA i PR trzymać w pliku poza repo. Nie używaj na to `${CLAUDE_PLUGIN_DATA}`, bo odinstalowanie domyślnie je usuwa ([manifest](https://code.claude.com/docs/en/plugins/manifest-reference.md)).

Plugin nie może być viewerem. Mody rysują ograniczone drzewo elementów, nie dowolny HTML ([Mods](https://code.claude.com/docs/en/plugins/mods/reference.md)), a Claude Code nie renderuje MCP Apps ([quickstart](https://claude.com/docs/connectors/building/mcp-apps/quickstart)). Browser pane w Desktopie otwiera lokalny HTML, ale nie ma udokumentowanego komentowania podglądu ([Desktop](https://code.claude.com/docs/en/desktop)). Biblioteka musi też działać bez sesji Claude'a, a manifest nie ma komponentu serwera. Mod przydaje się tylko jako panel z listą i `Link` do localhosta.

Interfejs dla człowieka to więc web: UI w przeglądarce na lokalnym procesie. Czysty PWA odpada, bo File System Access działa tylko w Chromium, obserwator żyje tylko przy otwartej karcie, a strona nie uruchomi `git` ani nie odpowie agentowi ([MDN BCD](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Window.json), [Chrome](https://developer.chrome.com/blog/file-system-observer)). Desktop odkładasz. Electron ma sens dopiero, gdy dokumenty zaczną przychodzić od innych lub z serwera firmowego, bo daje blokadę sieci na poziomie aplikacji ([Electron](https://www.electronjs.org/docs/latest/api/web-request)). Tauri nie ma przenośnego przechwytywania obrazu ([wry #1358](https://github.com/tauri-apps/wry/issues/1358)) ani ogólnego filtra żądań. Koszty podpisu ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)) nie decydują, dopóki używasz tego sam.

Zewnętrzny serwer plików nie zmienia dziś decyzji. Lokalny proces obsłuży S3, WebDAV i SFTP, a podstawą powinien być polling, bo powiadomienia o zmianach na udziałach sieciowych bywają niedostępne ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)). Priorytet zależy od protokołu serwera w pracy, którego jeszcze nie znamy.

## Test na Windows rozstrzyga, bo dziś wszystko jest deklaracją

**Zweryfikowane** jest niewiele: Twoja para Silos (pomiar koordynatora), statystyki repo z GitHub API, dokumentacja Anthropic oraz sondy sandboxa w Chromium na stronach testowych. Te ostatnie pokazały, że exfiltrację przez nawigację zatrzymuje `frame-src` strony nadrzędnej, a nie CSP dokumentu, oraz że POST z ramki dotarł do API z `Origin: null`. Firefox i Safari nie były testowane, a interfejsu claude.ai nikt nie otwierał, więc galeria i diff w Artifacts to stan dokumentacji. Sprawdziłem też, że w Node 22.14 na tym Windowsie `fs.constants.O_NOFOLLOW` jest `undefined`.

**Deklarowana** jest cała matryca. Windows: Plannotator, Crit i Lavish go dokumentują, ale nikt tego nie uruchomił. Artifact Server ma w CI zadanie dla macOS, nie dokumentuje wsparcia Windows i ma zgłoszenie „Publishing is impossible on Windows” ([#42](https://github.com/plannotator/artifact-server/issues/42)), zamknięte 23 września 2026 jako ukończone. Autor zgłoszenia uruchomił lokalną usługę przez MCP stdio na Windows 10, więc na tej platformie działała do etapu błędu, ale zgłoszenie dotyczy v0.1.0 i nie potwierdza stanu obecnego. Projekt wymaga Node 24.12 lub nowszego ([package.json](https://github.com/plannotator/artifact-server/blob/main/package.json)), a na tym komputerze jest Node 22.14, więc test zaczyna się od aktualizacji Node. Jego specyfikacja dokumentów powiązanych, czyli najbliższych Twoim folderom indeksowanym, opisuje serwowanie plików oparte na `O_NOFOLLOW` ([spec](https://github.com/plannotator/artifact-server/blob/main/project/spec/local-workspace-spec.md)), co przy powyższym wyniku jest konkretnym ryzykiem na Windows, choć nie czytałem kodu. Jest też sprzeczność: [strona w docs](https://docs.plannotator.ai/open-source/artifact-server) mówi o komentarzach tylko dla ludzi i kodzie source-available, a repo o narzędziach MCP i licencji MIT/Apache. Traktuję repo jako aktualne, ale werdykt od tego zależy. Nie sprawdzono roadmap, tempa przyjmowania PR-ów ani Reddita i X.

Test ma trzy bramki. Po pierwsze, serwer startuje lokalnie na Windowsie bez Dockera i chmury. Po drugie, v1 i v2 wchodzą jako dwie wersje jednego artefaktu, a generator zagadek i fonty działają. Po trzecie, komentarz przypięty w UI czyta `comment_list` i odpowiada na niego `comment_reply` z prawdziwej sesji Claude Code. Dokumenty powiązane sprawdź przy okazji, ale nie blokują: jeśli zawiodą, plugin publikuje kopię, a dokument zostaje na miejscu. Odpadnięcie którejkolwiek bramki oznacza rezygnację z Artifact Server.

Wtedy budujesz wąsko: web UI na cienkim demonie Node, CLI i stdio MCP czytające pliki bez demona, lokalne migawki, dwa originy, `sandbox="allow-scripts"` i CSP w nagłówku plus `frame-src` na powłoce, token na API. Rozdzielenie originów hosta i sandboxa wymusza też specyfikacja MCP Apps ([spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/2026-01-26/apps.mdx)). Warto sprawdzić, czy da się użyć `HtmlViewer` z `@plannotator/ui` ([spec](https://github.com/plannotator/artifact-server/blob/main/project/spec/artifact-comments-spec.md)), zamiast pisać nakładkę od nowa. Do czasu gotowego viewera pętlę komentarzy może dać Plannotator.

## Wniosek

Pytanie „budować czy nie” okazało się źle postawione, bo rozpada się na trzy warstwy o różnych odpowiedziach. Styl jest sprawą skilla i możesz go zacząć niezależnie od wyniku testu. Rejestracja z kontekstem repo to jedyny kod, który i tak musisz napisać. Viewer to część, którą warto pożyczyć, jeśli zadziała na Windows.

Największa zmiana po pomiarze: jeśli agent zwykle przepisuje dokumenty w całości, wartość leży w tym, by rozliczał się z otwartych wątków przy każdej nowej wersji, a nie w śledzeniu zmian tekstu. Ta dyscyplina należy do skilla, nie do viewera. Warto sprawdzić to na kilku kolejnych parach, zanim diff wróci do planu.
